FUTURE TASKS
============

Ideas for later. Not part of the current work (see TODO_TASKS.txt).


BACKEND (player data, achievements, login, authentication)
==========================================================

Goal: keep the game running in the browser; the backend only stores and verifies data.

Backend would own:
- Accounts, login and sessions
- Player profiles and stats (best run, credits, unlocks)
- Achievements
- Leaderboards

Stack options:
- Firebase (Auth + Firestore): fastest hackathon path, no server to write, built-in email/Google/GitHub login, free tier.
- Supabase (Postgres + Auth): SQL with built-in auth and row-level security, open source.
- Node.js + Express + database: full control, but you write the API, hashing and sessions yourself.
- Python (FastAPI/Flask): same tradeoffs as Node.
- Recommendation: Supabase or Firebase. Avoid hand-rolling authentication.

Security points:
- Never store plain-text passwords; use a managed auth service or bcrypt/argon2.
- Use HTTPS and secure session/token handling (httpOnly cookies or a provider's tokens).
- Do not trust the client: scores and achievements can be faked. Validate on the server where possible, or accept casual cheating.
- Keep server secrets off the frontend.
- Apply access rules so users only read/write their own records.

Preparing the frontend now:
- Put saving/loading behind one small module (saveProgress() / loadProgress()), using localStorage today and API calls later.
- Keep achievements and stats as plain data objects so they sync easily.
- Keep the game playable as a guest; login is only needed for online saves.
- A local dev server (and CORS handling) will be needed once an API is called.

Suggested order: guest play -> local save -> optional login with cloud save and achievements. Do authentication last.


PHASER 3 MIGRATION (when the game outgrows plain JS)
====================================================

Phaser is optional, not required. Move to it when adding sprites, animations, sound or many enemy types.

What it provides: game loop, rendering, Arcade physics, input, camera, scenes (menu/play/shop/game-over), asset loading, tilemaps, audio.

Port estimate for the current index.html (after the Vite/module split in TODO_TASKS.txt):
- Replaced by Phaser (~55%): game loop, input, physics/collision, camera, all drawing.
- Light edits (~35%): chunk generation, round/bonus/upgrade rules, enemy patrol, dot pickup.
- Unchanged (~10%): HTML/CSS HUD and syncHud().

Recommended stack: Phaser 3 + Vite, vanilla JS (TypeScript optional), HTML/CSS for menus, Supabase later for accounts/saves.
Keep game rules separate from drawing code so the port stays small.


3D VERSION (decided against for now)
====================================

- Staying with 2D; a 3D port would mostly be a rewrite of rendering, physics, levels and camera.
- Game design, state and rules would carry over.
- If ever revisited: keep game logic separate from rendering, use a position/vector abstraction, describe levels as data, and consider Three.js 2.5D as a stepping stone.
